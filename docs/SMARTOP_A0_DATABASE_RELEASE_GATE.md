# SmartOP การตรวจฐานข้อมูลก่อนส่งมอบระบบ

วันที่ 24 พฤศจิกายน 2569 — งานชุดแรกของ A0 ก่อนพัฒนาแกนบัญชีและภาษี

## ผลที่เพิ่มในระบบ

เพิ่มคำสั่งตรวจแบบอ่านอย่างเดียว หยุดการติดตั้งเมื่อพบฐานเดิมที่ยังไม่รับรองประวัติการปรับโครงสร้าง ชุดคำสั่งที่ถูกแก้ย้อนหลัง ประวัติที่ไม่อยู่ในรุ่นส่งมอบ การทำงานค้าง หรือโครงสร้างปลายทางไม่ตรงกับแบบข้อมูล ปรับขั้นตอนติดตั้งให้ตรวจประวัติก่อนปรับฐาน และตรวจโครงสร้างอีกครั้งก่อนเปิดโปรแกรม

งานนี้เป็นเครื่องมือและเงื่อนไขส่งมอบของ A0 ไม่ใช่การรับรองว่าฐานข้อมูลจริงผ่านการย้ายข้อมูล หรือว่างาน ERP-001 และ ERP-002 เสร็จทั้งหมด ยังต้องคืนสำเนาที่ได้รับอนุญาต ตรวจข้อมูลจริง สำรองและพิสูจน์การกู้คืน รวมถึงทดสอบบนระบบ Linux/MySQL 8 ก่อนขึ้นใช้งานจริง

## วิธีตรวจด้วยตนเอง

จากรากโครงการ ใช้ค่าการเชื่อมต่อส่วนตัวใน `.env` หรือกำหนด `DATABASE_URL` ในสภาพแวดล้อม ค่าที่กำหนดในสภาพแวดล้อมมีผลก่อนค่าจากไฟล์ ห้ามบันทึกไฟล์ความลับเข้าระบบควบคุมรุ่น

```sh
# ตรวจเฉพาะประวัติก่อนปรับโครงสร้าง อนุญาตให้มีชุดคำสั่งใหม่ที่ยังไม่ใช้
npm run db:preflight -- --history-only

# ตรวจหลังปรับโครงสร้าง ต้องใช้ครบและตรงกับแบบข้อมูลปัจจุบัน
npm run db:preflight
```

รหัสออก 0 หมายถึงผ่านเฉพาะขอบเขตที่ตรวจ รหัสออก 1 หมายถึงหยุดและให้ผู้รับผิดชอบตรวจสอบ ผลเป็นข้อมูล JSON ที่ไม่มีรหัสผ่าน ที่อยู่เชื่อมต่อ ข้อมูลแถวธุรกิจ หรือข้อความผิดพลาดดิบจากฐานข้อมูล

| ผลตรวจ | วิธีดำเนินการ |
| --- | --- |
| `LEGACY_BASELINE_REQUIRED` | คืนข้อมูลบนสำเนาที่อนุญาต ตรวจส่วนต่างและรับรองฐานอ้างอิงก่อน ห้ามบันทึกว่าปรับโครงสร้างสำเร็จทั้งชุดโดยไม่พิสูจน์ |
| `FAILED_OR_RUNNING_MIGRATION` | ตรวจการทำงานค้างและผลคำสั่งที่สำเร็จไปแล้ว ห้ามเริ่มซ้ำโดยไม่ตรวจ |
| `MIGRATION_CHECKSUM_MISMATCH` | ตรวจไฟล์ที่ถูกแก้หลังใช้งาน คืนต้นฉบับหรือทำคำสั่งแก้ใหม่ ไม่แก้ประวัติเพื่อให้ผ่าน |
| `UNKNOWN_MIGRATION` หรือ `MIGRATION_ORDER_MISMATCH` | ตรวจว่าใช้รุ่นส่งมอบและประวัติที่ถูกต้อง |
| `PENDING_MIGRATIONS` | หลังปรับโครงสร้างยังมีงานค้าง ห้ามเปิดโปรแกรมรุ่นใหม่ |
| `SCHEMA_DRIFT` | ตรวจส่วนต่างบนสำเนาและออกคำสั่งแก้ที่ทบทวนแล้ว ห้ามนำข้อความแนะนำจากเครื่องมือไปใช้โดยอัตโนมัติ |
| `SCHEMA_COMPARISON_UNAVAILABLE` หรือ `DATABASE_PREFLIGHT_FAILED` | ตรวจการเชื่อมต่อ สิทธิ์ ไฟล์ และเครื่องมือ ระบบจะไม่ถือว่าการตรวจไม่สำเร็จเท่ากับผ่าน |

เครื่องมือยอมรับความต่างของการขึ้นบรรทัด LF และ CRLF ในไฟล์เดียวกัน เพื่อรองรับ Windows และ Linux แต่ไม่ยอมรับการเปลี่ยนเนื้อหาคำสั่ง SQL

## ข้อจำกัดที่ต้องเข้าใจ

การตรวจ **ก่อน** ปรับโครงสร้างตรวจประวัติเท่านั้น ไม่ได้พิสูจน์ว่าส่วนต่างของฐานปัจจุบันเป็นส่วนต่างที่คาดไว้ทั้งหมด ต้องสำรอง ทบทวนคำสั่ง และซ้อมกับสำเนาก่อนใช้จริง การตรวจ **หลัง** ปรับโครงสร้างใช้เครื่องมือเปรียบเทียบของ Prisma ซึ่งตรวจตาราง คอลัมน์ ชนิดข้อมูล ค่าเริ่มต้น ดัชนีและความสัมพันธ์ที่ Prisma รองรับ ไม่ครอบคลุมกลไกอัตโนมัติในฐานข้อมูล โปรแกรมย่อย สิทธิ์ฐานข้อมูล หรือความถูกต้องของข้อมูลธุรกิจ

สถานะผ่านไม่แทนหลักฐานกู้คืน เงินเดือน ภาษี การทดสอบโดยผู้ใช้งาน หรือการอนุมัติเปิดระบบ

## การแก้ความคลาดเคลื่อนของชุดปรับฐาน

เพิ่ม `20261124000000_release_schema_alignment` โดยไม่แก้ไฟล์ประวัติเดิม

- เติมตาราง `PasswordHistory` ที่มีในแบบข้อมูลและโปรแกรมอยู่แล้ว แต่ขาดจากชุดคำสั่งย้อนหลัง หากสำเนาฐานที่รับรองมีตารางนี้อยู่แล้วจะคงตารางไว้ และใช้การตรวจปลายทางยืนยันโครงสร้างอีกครั้ง
- บนเครื่องที่แยกตัวพิมพ์ใหญ่เล็ก ให้เปลี่ยนชื่อ 4 ตารางสิทธิ์ตามชื่อที่แบบข้อมูลใช้อยู่ บน Windows ที่เก็บชื่อตารางเป็นตัวเล็กอยู่แล้วไม่เปลี่ยนซ้ำ รักษาชื่อดัชนีและข้อบังคับเดิมด้วยการระบุชื่อในแบบข้อมูล
- คงคอลัมน์ `User.password` ที่เลิกใช้ไว้เป็นคอลัมน์ละเว้นจาก Prisma Client เพื่อไม่ให้ตัวเปรียบเทียบเสนอให้ลบข้อมูลย้อนหลัง ไม่ใช้คอลัมน์นี้ตรวจรหัสผ่าน และไม่เปิดให้ส่วนแอปอ่านหรือเขียนผ่าน Prisma Client

ไม่เปลี่ยนขั้นตอนล็อกอิน การตรวจรหัสผ่าน หรือการจัดสิทธิ์ของโปรแกรมเดิม กรณีฐานที่ซ่อมเองบน Linux มีชื่อตารางต่างจากประวัติมาตรฐาน ต้องตรวจบนสำเนาและจัดแผนเฉพาะก่อนใช้คำสั่งใหม่นี้ ไม่ถือว่าครอบคลุมฐานที่คลาดเคลื่อนทุกรูปแบบ

## ขั้นตอนติดตั้งที่ปรับแล้ว

เส้นทาง PM2 ตรวจคุณภาพและเส้นทางระบบ ตรวจประวัติ ปรับโครงสร้าง ตรวจปลายทาง แล้วจึงเริ่มหรือโหลดโปรแกรมใหม่ หากขั้นใดผิดพลาด สคริปต์หยุดก่อนโหลดโปรแกรมรุ่นใหม่

เส้นทาง Docker มีงาน `migrate` ที่รอฐานข้อมูลพร้อม ตรวจประวัติ ปรับโครงสร้าง และตรวจปลายทาง ตัวโปรแกรมรอให้งานนี้สำเร็จก่อน และต้องกำหนด `AUTH_SECRET` เอง ไม่มีค่าความลับสำรองในไฟล์ติดตั้ง การใช้คำสั่งติดตั้ง Docker จะสร้างงานปรับโครงสร้างใหม่ทุกครั้งก่อนเปิดโปรแกรม

การติดตั้งยังเป็นการดำเนินการของผู้ดูแลตามแผนที่อนุมัติ ไม่มีการติดตั้งหรือปรับฐานบริษัทจากการพัฒนารอบนี้

คำสั่ง `npm run test:db:p3` ทดสอบทั้งงานคลังและตัวตรวจใหม่ โดยสร้างฐานใหม่ชื่อเฉพาะบนเซิร์ฟเวอร์ loopback เท่านั้น ฐานทดสอบถูกเก็บไว้เพื่อตรวจสอบ ไม่มีการล้างฐานเดิม ฐานสำหรับทดสอบตัวตรวจจะมีตารางสังเคราะห์เพิ่มโดยตั้งใจ เพื่อพิสูจน์ว่าตัวตรวจพบส่วนต่างและไม่ได้ลบหรือซ่อมให้เอง

บันทึกผลละเอียดอยู่ใน `tmp/p3-validation` และ `tmp/a0-*.log` ซึ่งไม่อยู่ในระบบควบคุมรุ่น

## งานถัดไปตามแผน

1. คืนสำเนาฐานเดิมที่ได้รับอนุญาต ตรวจความคลาดเคลื่อนและรับรองแผนฐานอ้างอิง ก่อนใช้ migration จริง
2. พิสูจน์การสำรองและกู้คืนฐานข้อมูล เอกสาร และกลไกอัตโนมัติ พร้อมเปลี่ยนหน้าจอที่ยังใช้สถานะจำลอง
3. ปิดช่องว่างตัวตนและขอบเขตสิทธิ์ที่เหลือ และแทนการคำนวณเงินเดือนจำลองด้วยข้อมูลและกฎที่บริษัทอนุมัติ
4. เมื่อเงื่อนไข A0 ผ่าน จึงเชื่อมข้อมูลหลัก ผังบัญชีและสมุดรายวันตามชุด A1
